# Colab：试一试开源模型能不能省钱

这一页回答一个问题：做片子要用开源模型时，Colab 上哪几类现在就能用、怎么用、坑在哪，能不能省钱。2026 年 11 月，我们每类挑了一个许可证允许商用的模型，在付费档上真跑了一遍。产物只用来判断能力，没有进成片。省钱这件事还没有结论：成本没有换算成同一把尺去比，零星出一两条不如即梦，一次开机多出几条才可能划算，替不替得掉商用服务都要人看过、听过再定。

先说清楚哪些结论可信。所有“听感”“画质”的判断，要么来自客观测量，要么来自 Gemini 盲听盲看的筛查；Gemini 判演法和听感不可靠（见 `review.md`），只能用来筛掉明显不行的，最后好不好由人自己听、自己看。我们还没有请人听过配音和配乐、看过超清，所以下面“替不替得掉商用服务”的结论都标成待定。

## 怎么在 Colab 上跑

用 Google 开源的 Colab 命令行（google-colab-cli 0.7.5，Apache-2.0，https://github.com/googlecolab/google-colab-cli），不用浏览器点，登录走 OAuth。常用命令：

- `colab new -s 名字 --gpu L4`（或 `--gpu A100 --high-mem`）开机；`colab usage` 看余额和每小时耗多少；`colab stop -s 名字` 关机。
- `colab exec -s 名字 -f 笔记本.ipynb --timeout 秒数` 按格执行一本笔记本，默认超时只有 30 秒，一定要给 `--timeout`；执行完会在本地存一份带输出的笔记本。
- `colab upload` / `colab download` 一次只传一个文件；目录先在远端打包。

我们的做法是每一类写一本笔记本，用脚本生成。这个仓库不附那些脚本，下面的每一节写出每一格要做的事和踩过的坑，足够你自己写。每一处修补我们都写了原因，下次直接重新生成。

Colab 上装环境有两个通用的坑：一是 Colab 预设了 `UV_SYSTEM_PYTHON`、`UV_CONSTRAINT`、`UV_BUILD_CONSTRAINT` 这几个环境变量，uv 会无视虚拟环境装进系统 Python 并套 Colab 的版本约束，装之前要 unset；二是系统 Python 是 3.13，有些库钉着旧版本，要另建 3.10、3.11 或 3.12 的环境。查环境变量只打印名字，不打印值。

## 一、中文配音

**模型**：Qwen3-TTS-12Hz-1.7B 的 CustomVoice（内置音色 Uncle_Fu、Serena，可以用一句话指挥语气）和 VoiceDesign（用一句话描述造一个声音）。备选 IndexTTS-2.5，音色参考用 VoiceDesign 自己造出来的整段旁白，情绪用八维向量或让模型读文字里的情绪。

**许可证**：
- Qwen3-TTS 代码 Apache 2.0。权重仓库没有单独的 LICENSE 文件，只有托管站标签和模型卡头部写 `license: apache-2.0`，证据比读到许可证全文弱一档。
- IndexTTS-2.5：bilibili Model Use License Agreement。第 2.1 条授予全球、免版税的使用许可；第 2.2 条规定月活过一亿或年收入过十亿元人民币要另外申请；第 3.4 条要求保留版权声明和协议副本、不得用它改进别的商用模型；第 6.1 条适用中国法律。按我们的读法，小账号远低于门槛；协议全文请自己读，以协议为准。
- IndexTTS-2（上一版）不能用：它要加载的语义编解码器是 CC-BY-NC-4.0。
- 打分用的 Whisper large-v3 标 apache-2.0，只用来打分，不进产物。

**做法**：另建 3.12 的 uv 环境，torch 钉 2.9.1（cu128 轮子）；`pip install qwen-tts`；注意力用 sdpa（没装 flash-attn，会打一行警告，不影响）；Qwen3-TTS 导入时要找 sox 命令，Colab 没装，要 `apt-get install sox`。IndexTTS-2.5 用官方的 `uv sync --python 3.11`，权重约 5.2 GB。首次跑会提示 “Ninja is required to load C++ extensions”，那是 BigVGAN 的自定义 CUDA 算子编不了、退回普通实现，不影响出声。

**数**：
- Qwen3-TTS 每个模型载入 25 秒左右；生成速度约是音频时长的 2.4 倍（4 秒的句子要 11 秒，20 秒的整段要 46 秒）。显存峰值 CustomVoice 4.3 GB、VoiceDesign 7.8 GB。
- IndexTTS-2.5 一句 6 到 12 秒，20 秒整段 24 秒，实时率 1.2 到 1.8；显存峰值 7.2 GB。
- 整本笔记本显存峰值 8.2 GB，L4 的 23 GB 绰绰有余。装环境加两套模型加打分，L4 上一共开机约 25 分钟，0.72 CU。

**听感能说到哪一步**：
- 字有没有念对：用 Whisper 听写的字错率在三句上分别是 0.07、0.04、0.25 上下，和同一三句的商用音色（豆包）一模一样。错的都是同音字，是 Whisper 认不出，不是声音念错。所以字错率在这三句上分不出高下。Gemini 盲听五段第三句，全都听出 jué shí，也说明念对了。
- Gemini 怀疑有四段第一句的字调不对，只是怀疑，要人听。
- 客观测到一个毛病：CustomVoice 的八段，最后 0.15 秒的响度还在 −25 到 −40 dB，等于话音没落就断了；VoiceDesign 和 IndexTTS 的十段结尾都是静音。用 CustomVoice 时，句末要多留一点文字或停顿再剪掉，或者干脆用 VoiceDesign。
- 语速：商用音色那三句每秒 4.4 到 4.5 个字，开源这边按“偏慢”的指令念，每秒 2.3 到 3.7 个字。要贴近商用音色的节奏，指令里别写“偏慢”。
- 打分脚本里的“音高起伏”一栏不可信（同一个声音读出 0.3 到 29 个半音），别看它。

**结论**：开源中文配音在 Colab 上能跑通，好不好听待人听：一台 L4、半小时以内、不到 1 CU，就能出一组二十段的试音，装法稳定。它能替片子做的，是低成本地多试几种读法、造一个固定的旁白音色；能不能替掉商用音色，要人听过再定。

## 二、配乐

**模型**：ACE-Step 1.5 XL turbo（4B 的扩散模型）加 1.7B 的规划语言模型，纯器乐。

**许可证**：代码 MIT；权重托管站标 MIT（只有标签，没有单独的 LICENSE 文件）；仓库 README 写明 “Generated music can be used for commercial purposes”，训练数据是授权曲库、公版和合成数据。

**做法**：官方要 Python 3.11 到 3.12，`uv sync --python 3.12` 按仓库锁定装；`acestep-download` 下主包，再 `acestep-download -m acestep-v15-xl-turbo --skip-main` 下 XL。语言模型用 PyTorch 后端，不用 vllm。装加下载约 2.5 分钟。

**数**：一段 60 秒约 30 秒、90 秒约 38 秒，其中扩散本身只要 2.6 秒，大头是语言模型先写“计划”。显存峰值 19 GB（L4 够用）。L4 上约 10 分钟，0.33 CU。

**坑**：
1. 种子写在 `GenerationParams(seed=...)` 里不生效，四段拿到的全是随机种子。要写在 `GenerationConfig(use_random_seed=False, seeds=[1234])`。
2. 默认 `use_cot_caption=True`，语言模型会改写你的描述：这次把 guqin 改成了 guzheng，把 xun 删了，整段描述换成它自己的话。想让指定的乐器出来，要设 `use_cot_caption=False`。

**听感（Gemini 筛查，不可靠）**：第一轮只有一段大致对路（听出古筝类弹拨、二胡、箫、大鼓，没听出编钟），另外三段都混进了现代编曲。改了上面两处以后在 A100 上重跑：一段这回听出古琴或古筝类的弹拨、箫、二胡，没有流行鼓了，最接近“孤寂苍茫”；两段“悲壮”还是钢琴、弦乐群、架子鼓的现代编曲；四段里一次都没听出编钟和埙；有一段结尾冒出一声孤立的鼓点，像没剪干净。应龙那期用的一段古琴拨弦加二胡、自带雨声的配乐，就是这样出的（`cases/yinglong.md`）。

**结论**：开源配乐在 Colab 上便宜又快，一台 L4 十分钟能出一批。它能给片子做的，是稀疏、安静的古风铺底；要“悲壮大场面”或点名的冷门乐器，它会往流行编曲上靠，控制不住。用之前先请人听。

## 三、超清和补帧

**问题**：开源的超清能不能替掉即梦的超清（按次扣积分）。

**模型**：超清用 SeedVR2-3B（fp16），走 numz 的命令行 `inference_cli.py`；补帧用 Practical-RIFE 4.25。

**许可证**：SeedVR2 权重仓库 README 写 “SeedVR and SeedVR2 are licensed under the Apache 2.0.”，代码仓库和运行器的 LICENSE 也是 Apache 2.0。Practical-RIFE 代码 MIT，README 写明权重同样是 MIT。

**输入**：帝江那一期即梦 Seedance 2.5 出的一条没用上的镜头（1280×720，121 帧，约 5 秒）。注意即梦文件头报 60 帧，实际是 24 帧每秒；拿 ffmpeg 直接放大会按 60 帧补出 301 帧，比对时要用抽出来的帧，不要按帧号对视频。

**做法**：SeedVR2 用系统 Python 和 Colab 自带的 torch，`pip install -r requirements.txt`，约 4 分钟；参数 `--batch_size 61 --temporal_overlap 4 --color_correction lab --latent_noise_scale 0.1`（批大小要是 4n+1）。RIFE 钉 numpy≤1.23.5，另建 Python 3.10 的环境，权重从官方网盘链接用 gdown 下。RIFE 4.25 的压缩包里自带 `train_log/` 目录（还夹着 `__MACOSX`），先解到别处再拷会静默失败，要直接解到仓库根目录。

**数**：
- SeedVR2 放到 1080P 用 252 秒（含第一次下 6.3 GB 权重），1440P 用 295 秒；5 秒的镜头要 4 到 5 分钟。输出保留 121 帧、24 帧每秒。显存峰值没测到。
- RIFE 把 Wan 出的 720P、16 帧每秒、81 帧的片子补到 32 帧每秒用 15 秒，补到 48 帧用 10 秒，再隔帧取一帧得到 24 帧每秒。快到可以忽略。

**画质（客观测量加看截图）**：
- 同一帧 1:1 裁同一块雪峰：SeedVR2 的山脊线和雪的纹理明显比 lanczos 放大清楚，没看到凭空编出来的东西。缩回 720P 和原片比，整段 SSIM 0.92，没改画面内容。
- 相邻帧差的平均值从原片的 1.19 升到 1.58；只量画面里不动的左上角天空，从 0.38 升到 0.61（灰度 0 到 255，裁成 320×216 后量），最大值 2.78 对 1.66。说明静止处有轻微的纹理游动，但幅度在 1/255 以下，平台压缩后大概率看不出。
- RIFE 补出来的中间帧在翅膀快速摆动的地方没看到重影或撕裂。

**结论**：开源超清在 Colab 上能用，画质上比简单放大有实打实的提升，成本是一个 5 秒镜头 4 到 5 分钟的 A100（约 0.6 到 0.7 CU，加开机和装环境的固定开销）。我们的暂定做法是：每条超清后量一次静止区域的相邻帧差，超过原片的两倍就退回原片或改用即梦超清。依据只是一条镜头的相邻帧差，没有拿同一镜头和即梦超清比过，没有人看过片，所以“能不能替掉即梦超清”仍是待定。RIFE 补帧可以直接用，Wan 出的 16 帧片子补到 24 或 32 帧没问题。

## 四、开源视频

**模型**：Wan2.2 I2V-A14B（diffusers 格式）加 LightX2V 的四步蒸馏 LoRA，走 diffusers，不走官方 generate.py（Colab 上编译 flash-attn 是已知的坑）。

**许可证**：Wan2.2 权重仓库 README 写权重按 Apache 2.0 授权，并且声明对你生成的内容不主张权利，代码 LICENSE 也是 Apache 2.0。LightX2V 的 LoRA 只有托管站标签和 README 徽章写 Apache 2.0，没有单独的 LICENSE 文件，证据弱一档。

**做法**：
- 另建一个借用系统 torch 的环境（`uv venv --system-site-packages`），装 diffusers 0.42.1、transformers 5.22、peft 0.21、torchao 0.18；uv 不把系统包算作已装，会往环境里装一份新 torch，和系统的 torchaudio 对不上，所以装完要把环境里的 torch、torchvision、torchaudio、triton、nvidia-* 卸掉，用回系统的 torch。用约束文件钉 `+cu130` 这类带后缀的版本不行：包索引上没有，整个解析失败。
- Colab 自带的 torchao 太旧，新版 peft 挂 LoRA 时报“版本太旧”；在单独的环境里装 `torchao>=0.16`。这个错要等 119 GB 下完、模型载入完才冒出来，白搭了一次约 5 分钟的载入，所以要在下载前先检查。
- 基础模型 119 GB（两个 14B 的专家模型按 fp32 存），A100 上从托管站下用了 5 分 46 秒，约 350 MB/s，不用登录。两个 LoRA 各 0.6 GB 左右。
- 载入（转成 bf16）：冷载入 312 秒，同一台机器第二次载入 171 秒；LoRA 两个专家各挂上 406 层；`enable_model_cpu_offload`。开的是高内存 A100：80 GB 显卡、167 GB 内存、236 GB 磁盘，都够。
- 下载和生成都用 nohup 在后台跑，日志写文件，再用短的 exec 去看。
- 视频存出来默认码率很低（720P 只有 0.7 到 1.2 Mbps），要进剪辑应该改存高码率或存帧序列。

**数**（每条 81 帧、16 帧每秒，约 5 秒，四步，种子 0）：

| 片子 | 分辨率 | 用时 | 显存峰值 |
|---|---|---|---|
| 图生视频，挂 LoRA | 832×464 | 154 秒 | 31.6 GB |
| 图生视频，不挂 LoRA（对照） | 832×464 | 113 秒 | 31.3 GB |
| 图生视频，挂 LoRA | 1280×720 | 231 秒 | 36.8 GB |
| 首尾帧，挂 LoRA | 1280×720 | 231 秒 | 36.8 GB |

一条 720P 约 4 分钟，约 0.57 CU。冷启动：装环境约 2 分钟、下载约 6 分钟、载入约 5 分钟，顺利的话开机后十三四分钟出第一条；这次因为 torchao 那个错多载入了一次，实际 23 分钟才出第一条。显存峰值 37 GB，40 GB 的 A100 也许够，L4 的 23 GB 不够。

**画质（看截图加客观测量）**：
- 不挂 LoRA 的对照在四步下糊成一团，说明 LoRA 确实生效了。
- 首尾帧那条最后一帧和目标尾图的 SSIM 是 0.949（只给首帧的几条只有 0.54 到 0.68），首尾帧控制真的管用；过程平滑，光圈一圈圈荡开，和尾图对得上。
- 和即梦比：帝江那一期用同一组关键帧出过 Fast VIP 的那条（720P，5 秒，30 积分）。两条几乎一样：六条腿全程站在峰顶，光圈一圈圈荡开，翅膀都只小幅摆动。Wan 这条 720P 的细节略糊一点，但不差。
- 图生视频（不给尾帧）那条翅膀扇得比提示词说的“几乎不动”大得多，运动幅度不太听话。

**再一次验证**：应龙的“全身滑翔”一镜，即梦出的龙身像一根硬管子，我们拿 Wan 试了两种出法，花 6.31 CU。只给首帧时画面整体在往前推、龙越变越大；首尾帧用同一张图时几乎是一张静图。详细的数字和做法在 `cases/yinglong.md` 的“事后的 Wan 重抽”。对长身带翼的龙，“身子起伏、翅膀不扇”这件事，两种出法都没有做到，这一点仍然空着（见 `open-questions.md`）。

**结论**：开源图生视频在 Colab A100 上能跑通，首尾帧控制在帝江那一组关键帧上管用，和即梦 Fast VIP 的那条看上去几乎一样（只有这一组，判断靠截图加 SSIM，没有人看过片）。代价是每次冷启动十来分钟加每条 4 分钟，一次开机出 4 到 8 条比较划算，零星出一两条不如即梦，成本没有换算过。可能适合的用法：手里有首尾关键帧、要把造型守住的镜头；镜头的运动幅度，帝江那组用尾帧约束住了，单靠提示词压不住；长身龙上的情况不同，见下一节。

## 五、图生三维、图像模型与许可证的坑

我们 2026 年 11 月读过这几个模型托管站上的许可证原文：

- Qwen-Image、Qwen-Image-2512、Qwen-Image-Edit-2511、Qwen-Image-Layered 标的是 Apache 2.0，按我们的读法可以商用，下载不用申请；最新的 Qwen-Image-2.1（含 Turbo）用的是研究许可，只许研究和评估，不能用于成片。
- 图生三维的 TRELLIS.2 本身是 MIT，但看图那一步要 Meta 的 DINOv3，得在托管站上申请、等人工审批；默认的抠图模型 RMBG-2.0 不许商用；渲染库 nvdiffrast 只许研究和评估，而且它导出模型和烘焙贴图那一步就用它。所以 TRELLIS.2 的结果只能拿来试，不能进成片。
- 腾讯的混元 3D 2.1，许可证排除了欧盟、英国和韩国这几个地区，月活一百万以下商用不用另外申请，下载也不用申请（仓库代码文件开头还写着旧的 NON-COMMERCIAL 字样，以 LICENSE 文件为准）。我们在 A100 上试过：从抠底到出带贴图的模型 5 分 23 秒（含下载模型），形状那步显存峰值 7.6 GB、贴图那步 13.4 GB，整轮连装环境和排错一共 6.53 CU（约 0.65 美元）。看得见的那一侧做得好，夔纹的浮雕是刻进几何体里的；但模型按左右对称补了看不见的那一侧，多长了一条腿，设计里的“一足”没了，顶面和背面的贴图发白、有竖条纹。事先读到的资料说贴图那一步要约 21 GB 显存，免费的 T4（16 GB）跑不了；实测峰值是 13.4 GB，我们没有在 T4 上试过。渲染上两个坑：pip 装的 bpy 要先 `import bpy`，`addon_utils` 和 `mathutils` 才导入得了；用显卡渲染两分半钟一张图也没出（原因没查实），改用 CPU 渲九张 512 的预览图不到半分钟。另外它钉的 bpy 4.0 已从包索引下架，要在笔记本里用系统 Python 装的 bpy 来做转换。
- 托管站上的免费演示（ZeroGPU）免费账号一天只有 300 秒，而 Qwen-Image-Edit-2511 官方演示每次报要 360 秒，所以免费账号永远跑不了。
- 有的开放权重的许可证按地区排除授权（排除若干国家和地区），要在你所在地区用，得另向官方申请。托管站上的量化版（社区出的）只省显存，地区限制照旧，标成 Apache 2.0 的也一样。下载前读 LICENSE 全文，不要只看标签。

## 踩过的坑（通用）

1. **开机后先跑一句最简单的命令。** 第一台 A100 开出来，`colab exec` 连不上内核（“Connection was lost”），命令行不报错、一直挂着，白白空转 25 分钟、3.53 CU。之后每次开机先执行一句 `print`，90 秒内不回就关机重开。
2. **`colab exec` 的退出码不可信。** 格子报错它也返回 0，要看输出里有没有报错。
3. **长任务不要挂在 exec 上。** 用 nohup 在远端后台跑，日志写文件，再用短的 exec 去看。
4. **上传不会自动建目录**，目标目录不存在就报 500，而且报错里会打出带运行时令牌的完整网址；上传到 `/content/` 再挪，命令输出截短再存。
5. **笔记本格子用 `%` 格式化会把 `%%writefile` 变成 `%writefile`**，那一格就不写文件。用占位符替换，不用 `%`。
6. **`%%bash` 里的 ffmpeg 要加 `-nostdin`**，不然它把后面的脚本当交互命令吃掉；Colab 也没有 `/usr/bin/time`。
7. **同一台机器跑第二本笔记本前，停掉上一本留下的 nvidia-smi 记录进程**，不然显存峰值会串。
8. **`pkill -f` 别经过 shell 调用。** `pkill -f '某串'; nohup …` 放在一个 `sh -c` 里，pkill 会连这个 shell 自己一起杀掉（它的命令行里也有那串字），后面的记录进程根本没起来，超清那一段的显存峰值因此没测到。要么在 Python 里 `subprocess.run(['pkill', '-f', ...])` 直接调，要么用 `pgrep` 拿到进程号再杀。
9. **本机的看守脚本里，每条 `colab` 命令都要另加超时。** 一批配乐跑完了，远端打包那一步报 `Connection was lost`，接着的下载命令卡住 15 分钟不返回，L4 一直开着，后来手动下载、关机。macOS 没有 `timeout` 命令，要用后台进程加 `kill` 自己写，日志停更超过几分钟就要去看。
10. **笔记本没有从头到尾整本重跑过。** 我们的修补是在 Colab 上一格一格修好、再写回生成脚本的；按最终写法跑过的是配乐 1 到 3 格、补帧两格、视频的安装格和 LoRA 解析格。没按最终写法跑过的：配音整本（只加了 sox 一行、改了打分的文件名判断）、超清那一格、视频的“后台生成”和“看进度”两格（这三处实际是手写的启动脚本）。你照着写时，先整本跑一遍再信它。
